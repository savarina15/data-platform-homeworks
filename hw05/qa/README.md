# HW5 — Network / Integration / QA

Компонент участника №4. `check_pipeline.py` автоматически проверяет цепочку
`Prefect Flow → Spark/YARN → HDFS Parquet → HiveServer2` только чтением.
Он не устанавливает сервисы, не вызывает `spark-submit`, не запускает Flow,
не создаёт таблицы, не выполняет `MSCK REPAIR`, не удаляет данные.
Повторный запуск безопасен; JSON-отчёту каждый раз нужно новое имя.

На 10.11.2026 в актуальном `main` нет реализации HW5. Поэтому Prefect выбран
**для QA-контракта**, согласно предпочтению задания; инфраструктура не создавалась.
Адрес Prefect, его версия и Flow пока не подтверждены. Если участник №1 выберет
Airflow, этот адаптер нельзя выдавать за проверку Airflow: потребуется согласовать
API и идентификаторы запуска и адаптировать QA до сдачи.

## Условие и границы подтверждения

По предоставленному скриншоту нужно в потоке Prefect или DAG Airflow запустить
Spark под YARN, подключиться к ранее развёрнутому HDFS, прочитать заранее
загруженные данные, выполнить несколько преобразований и сохранить таблицу.
Для 10 баллов необходимы все шаги без ошибок, инструкция и автоматизированные
скрипты; дедлайн — **20 ноября, 23:59**, просрочка — штраф 20%.

| Требование | Доказательство QA | Кто реализует шаг |
|---|---|---|
| Оркестрация | API отвечает; конкретный Flow правильного `flow_id` имеет COMPLETED и времена начала/конца | №1 |
| Spark под YARN | RM STARTED, конкретное приложение SPARK, FINISHED + SUCCEEDED, пользователь и tag Flow совпали | №3 |
| Предварительно загруженный HDFS | Явный `hdfs://host:port/path`, файлы и байты больше нуля | №2 |
| Чтение и преобразования | Конечные строки сравниваются с ожидаемыми; запуск связан с Flow, файлы свежие | №2; исходный код и лог Spark также нужны при сдаче |
| Сохранение как таблицы | Hive проверяет схему, LOCATION, COUNT, непустые партиции и чтение физических столбцов | №2 + включение регистрации таблицы в Flow №1 |
| Воспроизводимость | CLI, примеры конфигурации, локальные тесты, эта инструкция и JSON-отчёт | №4 |

QA по состоянию сервисов не доказывает внутреннюю логику произвольного приложения.
Для полной сдачи команда должна также показать исходный PySpark-код, несколько
преобразований, лог чтения HDFS и Flow/DAG. PASS относится к указанным ID и моменту
проверки; он не гарантирует сохранность результата при последующей перезаписи.

## Зависимости и конфигурация

Для QA нужны Python **3.9+** (stdlib), `curl`, Hadoop `hdfs`, Java и Beeline
с конфигурацией кластера. Для туннеля — OpenSSH, личный ключ и заранее проверенный
host key edge в `known_hosts`. Сторонние Python-пакеты и установка Prefect SDK
не требуются. API-адаптер рассчитан на self-hosted Prefect 2/3 с `/api/health`
и `/api/flow_runs/{uuid}`. Поддержку фактической версии нужно подтвердить на edge.

Запускать всю проверку рекомендуется на **edge**: там доступны внутренние DNS,
HDFS RPC/DataNode и клиенты. Один HTTP-туннель не даёт ноутбуку доступ ко всем
DataNode, поэтому проверка всего HDFS с ноутбука не обещается.
Переносите репозиторий целиком: QA переиспользует bounded transport и process-group
timeout из `shared/qa/check_cluster.py`, валидацию Hive из
`hw04-spark/qa/hive_integration.py`. Существующая HW4 `verify` не проверяет точную
схему, непартиционированные таблицы, связь Flow/YARN и свежесть; эти проверки
добавлены здесь. `apply` из HW4 автоматически **не вызывается**.

Из корня репозитория:

```bash
cp hw05/qa/pipeline.example.json hw05/qa/pipeline.local.json
```

Отредактируйте локальный JSON по данным участников №1–3:

| Поле | Значение и смысл |
|---|---|
| `prefect.api_url` | Полный HTTP(S) URL с портом и `/api`; пример `http://127.0.0.1:4200/api` предполагает сервер на edge |
| `prefect.flow_id` | UUID самого HW5 Flow; `null` в примере намеренно не позволяет получить общий PASS |
| `yarn.url`, `user` | HTTP RM, обычно `http://team-37-nn:8088`; пользователь приложения `team` |
| `input` | Полный HDFS URI входного каталога, без glob |
| `hive.jdbc_url`, `user` | HiveServer2, без паролей/токенов в URL |
| `hive.database`, `table`, `location` | Фактическая конечная таблица и полный HDFS URI её LOCATION |
| `columns` | Физические колонки в порядке Hive DESCRIBE: `{name, type}` |
| `partition_column` | Одна колонка `{name, type}` или `null` для непартиционированной таблицы |
| `expect_partitions` | Точный набор `column=value`; без партиционирования — `[]` |
| `min_rows` | Минимум строк, положительное целое |
| `expected_rows` | Точные строки в порядке `columns`, затем partition_column, все ячейки — строки; порядок строк не важен, дубликаты учитываются |
| `clock_skew_seconds` | Допуск рассинхронизации времени, 0–60 секунд, по умолчанию в примере 5 |

`expected_rows: null` отключает точное сравнение значений, но оставляет COUNT и
чтение образца. Для маленького учебного набора оставьте точное сравнение: оно
выявляет ошибочную агрегацию. Для большого набора согласуйте отдельный ожидаемый
результат с №2; одного положительного COUNT недостаточно для проверки логики.
Партиции в этом адаптере: один столбец, безопасные значения `[A-Za-z0-9_-]+`.
Сложные типы и многоколоночные партиции намеренно отклоняются до запросов.

**Пример повторяет контракт HW3/HW4 из `main`, а не доказанный HW5 результат:**
вход `/user/team/datasets/books`; фильтр year=2023; подсчёт жанров;
выход `/user/hive/warehouse/books_stats_2023`; таблица
`default.books_stats_2023_qa_team37`; `count BIGINT`, `genre STRING` — партиция;
по одной книге Fiction и Dystopia. Нельзя проверять изменённый датасет с этим
ожиданием. Пример не загружает данные и не регистрирует старую QA-таблицу.
Одинаковый HDFS authority во входе и результате обязателен.

Локальные конфигурации и `reports/` игнорируются Git. Не добавляйте ключи,
инвентари и секреты. Авторизация к API с токеном/Basic Auth этим CLI пока не
реализована; 401/403 — FAIL, требуется согласовать безопасный способ с №1.
Не отключайте TLS-проверку и не помещайте credentials в URL.

## Безопасный доступ к UI

Порт **4200 — предположение** до настройки №1. Уточните адрес по его конфигурации,
при необходимости измените `tunnel.local.json`. Не открывайте UI в интернет.
С ноутбука, из корня репозитория, сначала проверьте команду:

```bash
cp hw05/qa/tunnel.example.json hw05/qa/tunnel.local.json
python3 shared/qa/check_cluster.py tunnel \
  --config hw05/qa/tunnel.local.json \
  --edge team@178.236.27.186 --identity-file ~/.ssh/id_ed25519_team37 \
  --service prefect --service resourcemanager --dry-run
```

Для реального туннеля выполните ту же команду **без `--dry-run`**.
После подключения UI: `http://127.0.0.1:14200`, RM:
`http://127.0.0.1:18088/cluster`. SSH работает на переднем плане; Ctrl+C закрывает
туннель. Bind только на `127.0.0.1`, host key проверяется строго, forwarding
агента выключен. Dry-run проверяет только построение команды и не означает
успешного соединения. Открытие локального порта также не доказывает готовность API.
Для отдельного Beeline с ноутбука уже есть
[`open_hive_tunnel.sh`](../../hw03-hive/qa/open_hive_tunnel.sh).

Если системная SSH-конфигурация неисправна (`Bad owner or permissions ...`),
диагностическая команда без её чтения:

```bash
ssh -F /dev/null -i ~/.ssh/id_ed25519_team37 \
  -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=12 team@178.236.27.186 hostname
```

На этой рабочей станции обнаружена такая ошибка в
`/etc/ssh/ssh_config.d/20-systemd-ssh-proxy.conf`. Безопасный эквивалент туннеля
при этом локальном дефекте (после проверки фактического remote порта):

```bash
ssh -F /dev/null -N -T -a -x -i ~/.ssh/id_ed25519_team37 \
  -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes \
  -o ExitOnForwardFailure=yes -o ConnectTimeout=10 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:14200:127.0.0.1:4200 team@178.236.27.186
```

Не используйте `StrictHostKeyChecking=no` или слепое доверие `ssh-keyscan`.
Если host key отсутствует/изменился, сверяйте fingerprint по доверенному каналу.

## Контракт запуска с участниками №1–3

1. **№1** предоставляет настоящий `flow_id`, адрес/версию Prefect и завершённый
   `flow_run_id`; Flow должен дожидаться Spark и регистрации таблицы, падать при
   ненулевом коде любого шага. Запущенный фоновый Spark при COMPLETED Flow — ошибка.
2. **№3** использует свой существующий launcher; передаёт UUID текущего Flow
   в Spark YARN tag **`prefect-flow-run-id=<UUID>`** через
   `--conf spark.yarn.tags=prefect-flow-run-id=<UUID>`, сохраняя другие нужные tags
   через запятую. Возвращает/логирует точный `application_...` этого запуска.
   Значение UUID приходит от №1, не берётся из примера. QA сам ничего не submit-ит.
3. **№2 + №1** согласуют конечную таблицу и включают её создание/регистрацию и
   партиции внутрь Flow после записи Spark. Можно переиспользовать существующий
   HW4 инструмент регистрации после проверки контракта; QA HW5 не делает DDL.
4. Для проверки свежести нужен **полный снимок результата**: все `part-*` каждой
   ожидаемой партиции должны иметь HDFS mtime внутри интервала приложения с
   допуском. Входные файлы должны существовать до запуска Flow. При append или
   инкрементальной модели этот контракт нужно изменить осознанно; старые данные
   нельзя объявить доказательством записи данного запуска. Не запускайте проверки
   параллельно с перезаписью той же таблицы другим Flow.

Tag — часть согласуемого интеграционного контракта, а не требование скриншота.
Без него нельзя надёжно отличить приложение этого Flow от произвольной старой
успешной задачи. Неверный/отсутствующий tag у заданного приложения — FAIL;
отсутствующие ID/ещё не согласованный Flow — NOT TESTED.

## Запуск на edge после завершения реального Flow

Используйте отдельный личный checkout этой ветки; не переключайте общий checkout
команды. Пути ниже взяты из конфигураций `main` и требуют сверки на edge:

```bash
export JAVA_HOME=/usr/lib/jvm/java-11-openjdk-amd64
export HADOOP_HOME=/home/team/hadoop-3.4.0
export HADOOP_CONF_DIR="$HADOOP_HOME/etc/hadoop"
export PATH="$HADOOP_HOME/bin:/home/team/apache-hive-4.0.0-alpha-2-bin/bin:$PATH"
hdfs version
beeline --version
```

Из корня личного checkout выполните подготовку JSON выше, затем:

```bash
mkdir -p hw05/qa/reports
# Подставьте реальные идентификаторы из одного завершённого запуска HW5:
HW05_FLOW_RUN_ID='REPLACE_WITH_REAL_UUID'
HW05_YARN_APP_ID='REPLACE_WITH_REAL_APPLICATION_ID'
python3 hw05/qa/check_pipeline.py \
  --config hw05/qa/pipeline.local.json \
  --flow-run-id "$HW05_FLOW_RUN_ID" --application-id "$HW05_YARN_APP_ID" \
  --timeout 90 --report "hw05/qa/reports/run-$HW05_FLOW_RUN_ID.json"
```

Значения `REPLACE_...` намеренно невалидны: без реальных ID проверка не начнётся.
Для повторного запуска укажите новое имя отчёта. `--hdfs-bin` и `--beeline-bin`
позволяют передать абсолютные пути без изменения PATH; `--help` показывает CLI.
Проверка не ждёт завершения Flow: RUNNING/SCHEDULED и незавершённый YARN — FAIL,
запускайте после окончания оркестрации. Таймаут применяется **к каждой** команде,
а не ко всей цепочке; timeout убивает всю локальную группу процессов, включая Java.
Никакая удалённая Spark-задача не отменяется.

Диагностика до готовности Flow запускается той же командой без обоих ID;
зависимые проверки будут NOT TESTED, доступные сервисы и таблица проверятся.
Это не способ получить общий PASS до интеграции.

| Результат / exit | Значение |
|---|---|
| `PASS / 0` | Все 7 стадий реально пройдены в данном запуске QA |
| `FAIL / 1` | Есть проверенная ошибка: недоступный настроенный сервис, timeout, неверное состояние/схема/данные/mtime |
| `NOT TESTED / 2` | Нет FAIL, но не выполнен хотя бы один шаг: нет клиента, ID или согласованного Flow |
| `NOT TESTED / 2` до проверок | Ошибочная конфигурация, аргументы или путь отчёта |
| `130` | Проверка прервана пользователем/SIGTERM; полный результат не получен |

Если одновременно есть FAIL и NOT TESTED, общий код **1**; стадии сохраняют
свои статусы в JSON. Структура отчёта: `status`, `exit_code`, `checked_at`, оба ID,
`checks[]` с `check`, `status`, `detail`. Существующий отчёт не перезаписывается.
Ошибка записи отчёта после проверок даёт FAIL/1 и не маскирует ошибки сервисов;
предварительно обнаруженный существующий файл — ошибка аргументов, exit 2.
Не коммитьте сырые runtime-логи; перед передачей отчёта проверьте диагностический
вывод сервисов на конфиденциальные сведения. Образцы из unit-тестов не являются
кластерными доказательствами.

## Автоматические локальные проверки

```bash
python3 -m py_compile hw05/qa/check_pipeline.py hw05/qa/tests/test_pipeline.py
python3 -m unittest discover -s hw05/qa/tests -v
# Регрессия переиспользуемых компонентов:
python3 -m unittest discover -s shared/qa/tests -v
python3 -m unittest discover -s hw04-spark/qa/tests -v
bash -n hw03-hive/qa/open_hive_tunnel.sh
git diff --check
```

Тесты HW5 проверяют positive/negative сценарии всей цепочки, несвязанный Flow,
неуспешный YARN, устаревшие файлы, схему/LOCATION, данные/партиции,
непартиционированный результат, некорректный JSON/SQL injection, отсутствие
зависимостей, HTTP 503/redirect/HTML вместо API, недоступность/timeout, прекращение
дочернего процесса, CLI-коды и отчёт. Используются синтетические ответы,
исполняемые заглушки и настоящий **локальный** HTTP-сервер на случайном loopback
порту. Последнему требуется разрешение на локальные сокеты в sandbox.

## Ошибки и действия

| Симптом | Что проверить / кому исправить |
|---|---|
| SSH banner timeout | Доступность edge/VPN/firewall/актуальность IP у владельца инфраструктуры; сервисы не перезапускать |
| Address already in use | Свой старый туннель или другой local_port в JSON; не завершать чужие процессы |
| Prefect 404/HTML/401 | API URL с `/api`, версию/маршрутизацию/авторизацию №1; HTTP 200 страницы login не считается API |
| Нет `hdfs` / Beeline | Запустить на edge или указать `--*-bin`; это NOT TESTED |
| Вход HDFS пуст / AccessControlException | Путь, загрузку и права чтения №2; QA ничего не загружает |
| Flow не COMPLETED | Лог Flow и коды launcher у №1/№3; не подставлять ID прошлого успешного запуска |
| Нет YARN tag / интервал отличается | Передачу UUID и ожидание завершения у №1/№3 |
| Hive table not found / нет партиций | Сохранение/регистрацию в Flow у №2/№1; успешный Parquet сам по себе не является таблицей |
| Схема/LOCATION/строки отличаются | Контракт №2 и локальный JSON; не исправлять таблицу автоматически ради PASS |
| Result freshness FAIL | Полный снимок против append, mtime, рассинхронизацию часов, чужую перезапись; не менять timestamps вручную |
